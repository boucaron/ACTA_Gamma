# Plan: remove the raw-SQL `db exec` action from `acta_cli`

Status: proposal (not started)

## Context

`acta_cli db exec` is the only path that runs user-supplied SQL against the
audit database. Every reviewer round flagged it ("a loaded gun"): even with the
implemented mutating-only guard (leading `SELECT` rejected with exit 4), it can
still `DROP TABLE execution_log` or `DELETE FROM executions` with no
confirmation, no transaction wrapper, and no undo — inside a project whose
entire value proposition is an immutable, auditable record. The README warning
and the `docs/DBDesign.md` "never composed from user-supplied input" contract
are documentation, not enforcement.

The raw-SQL path exists only for two jobs:

1. Bootstraping a fresh database (applying `schema.sql`) for CLI-only users.
2. Manual schema evolution ("manual `ALTER TABLE` recipes are the supported
   way to move a file forward" — `docs/DBDesign.md`).

Both jobs can be done without accepting arbitrary SQL.

## Scope

**Remove** the `db exec` action from `acta_cli`:

- Handler in `acta_cli/src/commands/db.c` (`cmd_db` `exec` branch,
  `usage_exec`, the `{"exec", ...}` tools-table row, the `--sql` / `--file` /
  `--sql_stdin` plumbing, the 64 KiB cap, the KI-5 SELECT guard).
- The `db.exec` entry in `acta_cli/src/tools.c` (table drops 75 → 74 entries;
  bump the `--tools` schema `version` 2 → 3 and update the `tools` test
  expectations, including the 75-entry count in
  `acta_cli/tests/tools/tools_test.c`).
- Tests in `acta_cli/tests/db/db_test.c` that drive `db exec` (positional
  form, `--sql`, `--file`, `--sql_stdin`, KI-1, KI-5 regression pins).

**Keep** `acta_db_exec` in `acta_db` — it is the DB-layer primitive, not the
CLI surface. Its only remaining caller is the GUI's first-launch schema
application (`acta_gui/src/mainwindow.cpp`). Update its header comment in
`acta_db/include/db.h` and the `docs/DBDesign.md` "One raw-SQL escape hatch"
paragraph to say the only caller is the GUI first-launch schema application.

## Replacement: `db init`

A new action that applies **only** the canonical static schema — no user
SQL, no flags carrying text:

```
acta_cli db init
```

- Applies the canonical `schema.sql` (idempotent: it is written with
  `CREATE TABLE IF NOT EXISTS` / `CREATE TRIGGER` guards, so re-running on an
  existing DB is a no-op; add the `PRAGMA table_info` idempotency check
  already referenced in `docs/DBDesign.md` to detect a partially-applied or
  foreign file and fail closed with a clear error).
- Output contract: `{"status":"ok"}` (matching `db backup`), exit 0;
  non-schema or half-applied file → hard error with exit 4 and a stderr
  message naming the mismatch.
- The canonical file moves from `acta_gui/db/schema.sql` to `acta_db/schema.sql`
  (the persistence layer owns its own schema; this also fixes the
  "schema lives in the GUI tree" papercut from the README cross-check).
  The CLI embeds it as a generated C header (e.g. `acta_db/schema_sql.h`,
  generated by a `make` rule from `acta_db/schema.sql` — single source of
  truth, same approach as the GUI's Qt resource `:/db/schema.sql`); the GUI
  resource is regenerated from the same file. `acta_cli` / `acta_runner`
  then never need to read a path from the repo, and the README bootstrap
  becomes: `acta_cli db init` (or launch the GUI once).

## Schema evolution policy (replaces "manual `ALTER` via `db exec`")

With `db exec` gone, there is no operator path for ad-hoc DDL. The supported
paths become:

1. **New DB file** for a clean state (already documented as the
   clean-state path).
2. **Versioned schema file**: the next schema change lands as a new
   `schema.sql` revision plus a note in `docs/DBDesign.md`; existing files
   that need the change are migrated by the operator taking a
   `db backup --to` first, then re-applying via `db init` on a fresh file
   (data-carrying files are migrated in a follow-up, below — deliberately
   out of scope here).
3. `PRAGMA user_version` + static `db migrate` scripts: **follow-up**, not
   part of this plan — see Open questions.

## Documentation updates

- `README.md`
  - Quick start / "Fresh databases need the schema first":
    `acta_cli db init` as the CLI path; mention the GUI path.
  - "CLI ergonomics": delete the `db exec` warning paragraph entirely.
- `docs/cli_spec.md`
  - Delete the `db exec` row (flag table, wire format, the
    "mutating-only" paragraph, the `{"status":"ok"}` success line) and add
    the `db init` row.
- `docs/DBDesign.md`
  - "One raw-SQL escape hatch": only caller = GUI first-launch schema.
  - Durability/backup section: "schema changes via `db exec`" →
    "schema changes via the versioned schema file / `db init`".
  - Canonical schema path: `acta_db/schema.sql`.
- `docs/status.md`: add a Done note for the removal (what changed, test
  pinning, `--tools` version bump).
- `docs/known_issues.md`: history stays as-is (it is a closed-issue log);
  no new open row — this is a design change, not a bug fix.

## Test plan

- `acta_cli/tests/db/`: new suite/scenarios for `db init` —
  - fresh empty file → schema applied, `{"status":"ok"}`, exit 0;
  - re-run on an existing schema'd file → no-op, exit 0;
  - file with a partial/foreign schema (e.g. `schema.sql` minus one table,
    or an unrelated table present) → hard error, exit 4, clear message;
  - `db exec` in any form (positional / `--sql` / `--file` / `--sql_stdin`)
    → unknown-action exit-10 (same as any other rejected action).
- `acta_cli/tests/tools/`: entry count 74, `db.init` present, `db.exec`
  absent, `version` 3, `success` shape for `db.init` (`json`, keys
  `["status"]`).
- `acta_runner/tests` and `acta_db/tests`: unaffected, except anything that
  seeds from `acta_gui/db/schema.sql` must point at `acta_db/schema.sql`
  (`acta_runner/tests/README.md` mentions the seed path).
- GUI smoke: `acta_gui/db/smoke_test.sh` still passes with the moved
  canonical file (Qt resource regenerated).

## Verification

- `make all`, `make test` (all suites green, including the updated `tools`
  suite and `db` suite).
- `make gui` builds with the regenerated schema resource.
- Grep audit: no remaining user-facing `db exec` references in
  `README.md`, `docs/`, `--help` output, or `--tools` output
  (historical mentions in `docs/known_issues.md` / `docs/status.md` fix
  history are intentionally kept).

## Breaking changes / compatibility

- CLI-only, POC-stage project: no external scripts are expected to depend
  on `db exec`. No deprecation window — removal is direct. `db version`,
  `db backup`, and `db help` remain.
- Scripts that used `db exec --file ...schema.sql` to bootstrap a fresh DB
  switch to `acta_cli db init`.
- `--tools` consumers (any scripted surface) must bump their expectations
  (version 3, 74 entries).

## Open questions

1. Should `db init` also accept `--force` to re-run `PRAGMA integrity_check`
   on the existing file before applying (defense-in-depth for a corrupt
   file)? Default: no; plain idempotency check is enough for the POC.
2. When the first real schema change lands, do we adopt `PRAGMA user_version`
   + `db migrate` with repo-static migration scripts (follow-up plan), or
   keep "new DB file" as the only evolution path?
3. Should `acta_db_exec` eventually be marked internal
   (`acta_db/include/db_internal.h`) now that its only caller is in-process
   GUI code? Defer; it still has one legitimate caller.

## Rollout (single logical change)

1. Move `acta_gui/db/schema.sql` → `acta_db/schema.sql`; regenerate GUI
   resource; add the CLI embedding (generated header + `make` rule).
2. Remove the `db exec` handler/help/tools entry; add `db init`.
3. Update tests (`db`, `tools`, seed paths), docs (README, cli_spec,
   DBDesign, status), and the `--tools` version bump.
4. Run the full suite + GUI smoke test.
