# Current status

Early prototype / POC — not a product. By design (see `docs/DBDesign.md`, "Scope and assumptions"): no schema versioning or migration framework, no purge/hard-delete of rows (create a new DB file if a clean state is needed), and `acta_db` is not thread-safe — each consumer (CLI, runner, GUI) owns its own single connection, and simultaneous writers on one file are out of scope.

**Done:**

- Entity model and persistence: C library + CLI + GUI over SQLite.
- Skill/model versioning and folder organization.
- Execution lifecycle and execution log (`execution_log` phase rows).
- Replayable immutable contexts. `context create` derives the content hash when omitted: SHA-256 of the content, lowercase hex — the same rule the GUI applies (SHA-256 implementation from Brad Conte's crypto-algorithms, public domain; see `acta_cli/src/sha256.c` and the README "Third-party code" section). An explicitly supplied `--hash` / JSON `hash` is stored as-is.
- Standalone runner (`acta_runner`): claim → resolve → preflight → OpenAI-compatible chat call → raw response capture → optional output-schema validation → complete/fail (see `docs/runner_contract.md`).
- In-app "Run" button: the GUI runs the runner's pipeline in-process on a worker thread, directly using the same runner source files (`acta_runner/src/run.c`, `acta_runner/src/backend.c`) — one shared pipeline codebase, no duplicated pipeline logic — on its own DB connection, with live status polling of the shared database. While a run is in flight the button toggles into Cancel, which cooperatively cancels the run and transitions the row to `cancelled`.
- `sweep` (`acta_runner sweep --stale-seconds N`) cleans up executions left in `running` after a dead runner process: an execution is stale when its last runner activity — the latest of its newest `execution_log.created_at` and `started_at` (falling back to `created_at`) — is older than `now − N` seconds. A stale row transitions `running → failed` with the error `stale running: no runner activity for N s` and an `execution_failed` log row; any row that leaves `running` between the query and the fail is skipped rather than overwriting a live outcome. `--stale-seconds` is required (there is no default) and must be a positive integer (0 is rejected).
- Normal timeout handling is done by the runner itself (hard per-call HTTP timeout, `--timeout`, default 300 s), and rerun of failed executions (`failed → pending` via `acta_db_execution_reset`, exposed by the GUI Retry button and by `acta_cli exec reset <id>`).
- Soft-delete lifecycle for contexts and executions: complete at the DB layer (`acta_db`) — `delete` / `restore` flag flips, live-only lister defaults, `_with_deleted` / `include_deleted` variants, `create` refuses deleted contexts, `reset` refuses deleted executions; exposed in the CLI (`acta_cli`: `context delete/restore`, `exec delete/restore`, `--include_deleted` / `--deleted` on `get` / `list` / `count`, `deleted_at` in JSON/table output, `tools.c` (T3) rows, deleted test suites) and in `docs/cli_spec.md`; the `acta_runner` single-claim `deleted_at` guard and its claim test suite are in; and exposed in the GUI (`acta_gui`: `ExecutionPanel` show-trash list with per-row Delete/Restore and Retry disabled for deleted rows, `ExecutionCreateDialog` live-only context picker with deleted parents still offered, and `ContextPanel` show-trash list with per-row Delete/Restore) — design rules and the one-time DB migration are in `docs/DBDesign.md`; the GUI is implemented and manually smoke-verified (`acta_gui/db/smoke_test.sh` against a migrated DB).

- Light-projection listers for the high-volume entities (resolves known issue 1): `acta_db_context_query_light` / `_with_deleted_light` and `acta_db_execution_query_light` omit the blob columns (`content`; `prompt` / `raw_response` / `result` / `error`) — blob fields are `NULL` in returned rows, struct shapes and pagination unchanged; covered by `acta_db/tests/test_light_queries.c`. Adopted by: `acta_cli` `context list` / `exec list` (light by default, `--full` for blobs), the GUI (`ContextPanel::reload`, `ExecutionPanel::reload`, `ExecutionCreateDialog::loadParentExecutions`), while single-row getters (`context get`, `exec get`, `acta_db_execution_get` polls) and the create-dialog context tooltip keep the full blobs. UI trade-off: the context panel filter matches Type + Date (no content search, since the blob is no longer materialized in the list).
- Open-time pragma check-and-report (resolves known issue 2): `acta_db_open` captures the `PRAGMA journal_mode=WAL` / `PRAGMA foreign_keys=ON` results and queries the effective `PRAGMA journal_mode;` (the set-pragma can return OK while silently staying non-WAL, e.g. on `:memory:`). On degradation it stores an informational note in `last_error` — the open still returns `ACTA_DB_OK` and the connection is fully usable; the note is cleared by the next `acta_db_exec*` call. Documented in the `acta_db_open` header comment and `docs/DBDesign.md` (Scope and assumptions); the GUI (`DbHandle::open`), CLI, and runner warn on the note after a successful open. Covered by `test_db_open_file_wal_active` and `test_db_open_memory_wal_note` in `acta_db/tests/test_db.c`.
- `acta_db_exec` contract documented (resolves known issue 3): the `acta_db_exec` header comment now states that `sql` must be static/developer-supplied (DDL, migrations, schema scripts), never composed from user-supplied input, and lists the intended callers (GUI first-launch `schema.sql`, CLI `db exec`); the constraint is also in `docs/DBDesign.md` (Scope and assumptions).
- Per-action help in `acta_cli` (help review P0): `X help <action>` and `X <action> --help` print a single action's section for every entity; bare `X help` / `X --help` / `--help` keep printing the full entity help / global usage. Both entry points funnel into the same per-entity action→section lookups (`X_help_for_action`), so they cannot drift; `db` and `context` help were refactored into header + section functions + footer (single source of truth), and `parse_globals` no longer short-circuits on `--help` (it collects the entity/action tokens for routing; unknown entity or action with `--help` is the canonical exit-10 JSON error). Covered by the new `acta_cli/tests/help` suite and the `tests/gparse` help-routing seam tests. Analysis and plan: `docs/cli_help_analysis.md`, `docs/cli_help_plan.md`.
- Structured `success` in `acta_cli --tools` (help review P1, commit `1bb0466`): per entry, `success` is now a JSON object `{"kind":"json"|"json_object"|"json_array"|"bare_int"|"plain_text"}` — kind `"json"` carries the exact wire `"keys"`, an optional `"note"` carries the `--table` / `--count` variants — replacing the prose string; the schema `version` is bumped 1 → 2 in both the full JSON and the `--tools --compact` header. Implementation in `src/tools.c` (`tool_success_t` + `suc_*` constants + `jf_success` renderer); `tests/tools` (T4) expects version 2 and checks the per-entry `success` shape; the wire-format contract paragraph is in `docs/cli_spec.md`. Verified in the rebuilt binary (`test_tools` passes). Analysis and plan: `docs/cli_help_analysis.md`, `docs/cli_help_plan.md`.
- Help small fixes in `acta_cli` (help review P2): the `--db` line in `help_print` (`src/commands.c`) documents the default DB path (`$ACTA_DB`, else `./acta.db`), and `tools_print_compact` (`src/tools.c`) only emits the ` / ` required/optional JSON separator when the required list is non-empty, so `skill.update` renders `json:name,prompt_template,folder_id,description,output_schema` instead of `json: / name,…`. No schema or test-shape change.
- Download ergonomics in `acta_cli` for the high-volume payload data (`context.content`, execution `prompt` / `raw_response` / `result` / `error`; analysis in `docs/cli_download_analysis.md`): **P1** the `--tools` schema now advertises `--full` on `context.list` / `exec.list` with a `success.note` documenting the light default (commit `427671a`); **P2** a stderr warning when `--fields` names a light-omitted field without `--full` (silent-null trap; exit code unchanged, `740a3c6`); **P3** global `--out <path>` (whole stdout payload to a file, fd-1 redirect in `main.c`, stderr untouched, unopenable path → exit 10) and `--raw_out <field>` for `context get` / `exec get` (one raw unescaped field, precedence over `--id_only`/`--table`/`--fields`, `d820c6b`); **P4** large-payload file input — `context create --content_file`, `exec set-raw --raw_file`, `exec complete --result_file` (raw file content, mutually exclusive with the inline flags and, for `--content_file`, with `--json`/`--stdin`/`--from_file`; conflicts/unreadable file → exit 4, `0ce3886`); **P5** `--stream` on every `list` action — NDJSON, one JSON object per line, internal paging until the filter is exhausted (`--offset` start, `--limit` cap), mutually exclusive with `--count`/`--table`/`--id_only` → exit 4 (`a830bf2`). All registered in the `--tools` schema, `--help`, and per-action help; covered by the `tools` test suite; wire contract in `docs/cli_spec.md`.

**Known issues:** all three resolved: issue 1 (listers materializing full blob columns) via the light-projection listers above; issue 2 (pragma failures ignored at open) via open-time check-and-report; issue 3 (`acta_db_exec` raw-SQL escape hatch) via the doc-comment contract.

**Out of scope — we do not implement these:** automatic retries (owner decision, 2026-09-12 — retrying without knowing the cause is pointless); streaming responses (owner decision, 2026-07-10). A failed execution is retried manually via the `failed → pending` reset (GUI Retry button / `acta_cli exec reset <id>`).
